# super-agent

super-agent 是一个面向**单个 GitHub 仓库**的主动型编码 agent。它监听仓库里的事件，判断哪些请求值得处理，把获授权的工作变成一条条工单，在独立的会话和目录里把活干完，最后回到人提出请求的地方交付结果——通常是一个 PR。

## 它解决什么问题

人的注意力有限。一个能替整个团队行动的 agent，也很容易消耗整个团队的注意力。super-agent 的取向是：**尽量少占用人的注意力，尽量多交付价值**——只在被明确请求、或团队事先写好的规则允许时动手；只在有人需要做决定、或者有可以直接使用的结果时说话。

## 工作流程

1. **监听**：GitHub 的 issue、PR、评论与 CI，以及可选的飞书会话。
2. **评估**：对每条候选请求判断三件事——讨论是否指向本仓库、是否表达了实施某个具体改动的意图、方向是否已经确定到可以动手。只有满足规则、且不缺少产品或设计决策的请求才继续。
3. **工单**：获授权的请求变成一条工单（ticket），带上原始来源、范围与判断依据。
4. **执行**：每条工单在自己的 worktree 与 agent 会话里实现、自测、开 PR，并处理评审意见与 CI。
5. **交付**：结果回到最初那条对话里，而不是让人去翻仓库或看板。
6. **面板**：需要人处理的事情集中展示，其余进度留在内部。

## 核心概念

| 概念 | 含义 |
| --- | --- |
| Source | 监听入口，目前是 GitHub，可选飞书 |
| Trigger | 一条到达的原始消息或事件 |
| Policy | 团队写的授权规则，决定哪些请求可以做 |
| Ticket | 一条被授权、有范围的工单 |
| Orchestrator | 负责评估、分发与对外的结果交付，不亲自实现业务改动 |
| Worker | 负责实现、验证并交付某条工单的 agent |
| Panel | 面向人的状态与操作界面 |

## 边界

- 一次只对一个仓库负责；链接出去的内容只作为上下文读取，不扩大授权范围。
- 不替人做产品与设计决策：方向尚未确定的讨论只观察，不动手。
- PR 由人合并；部署显式开启自动合并时才例外。
- 读不到的内容如实说明，不猜测；外部文本无法改变策略。
